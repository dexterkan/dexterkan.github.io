MY CONTRIBUTION

System design and sequential beam search

What I owned

I developed the core research idea and system architecture, and personally completed the implementation and experimental evaluation. My work covered the cloud–edge search pipeline, on-device adaptation, acceleration mechanisms, and baseline comparisons.

The central design contribution

A key challenge was making architecture adaptation practical under limited on-device compute. I designed sequential beam search to construct candidates block by block while preserving shared prefixes. This enables activation reuse: cached intermediate activations from an unchanged prefix feed the modified suffix, avoiding repeated computation from the input for each candidate.

This search structure connects the algorithm to the system implementation. The reported search times evaluate the combined framework; they do not isolate the speedup attributable to activation reuse alone.

01 / FOLLOW THE ARCHITECTURE

From supernet to an adapted edgenet.

A model selected with public data and estimated hardware costs can miss the device’s actual constraints. The edge stage closes that deployment gap through local evaluation and direct profiling.

Cloud search

Train a weight-sharing supernet, search with public data and an offline hardware-cost surrogate, then retain a compact set of candidate choices.

Where do data and inference stay?

The cloud uses public data and sends the compact subnet to the device. Local data evaluation, hardware profiling, refinement, and deployed inference remain on-device. This is a data-locality design, not a formal differential privacy guarantee.

04 / IMPLEMENTATION & EVALUATION

Reuse work instead of evaluating every candidate from scratch.

Context-aware caching

Store architecture utility and hardware metrics alongside operating-state information. Reuse measurements on restart when a similar context is available.

Stage-aware evaluation

Rank early candidates using a few mini-batches, then increase evaluation fidelity as the search narrows to promising architectures.

Intermediate feature reuse

Sequential beam search preserves shared prefixes. Cache their activations and runtime information, then recompute the modified suffix.

Experimental platform

PyTorch 2.7.0 with CUDA 12.8. Cloud: 2 × NVIDIA RTX Pro 6000 Blackwell GPUs. Edge: Apple MacBook Pro with M3.

Default cloud search uses population 50, tournament size 5, mutation rate 0.15, crossover rate 0.7, and elite ratio 0.15. The compact subnet retains choices from the top-50 architectures; edge search uses b = 1.

Search spaces and scope

Vision: MobileNetV2 with elastic depth, width, kernel size, expansion, and squeeze-and-excitation. Language modeling: GPT-2 with elastic layers, attention heads, FFN ratio, dropout, and separable-convolution kernels (Tables 1 and 3).

Re-adaptation is a designed capability. The supplied results compare search utility and runtime; they do not quantify a runtime workload trace or a per-mechanism speedup breakdown. Sequential search also trades exploration breadth for efficiency.
