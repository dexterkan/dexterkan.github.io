ONGOING RESEARCH · FEBRUARY 2026–PRESENT

Selective cloud verification for LLM generation

A small model drafts locally. A learned gate decides which 8-token spans need verification by a larger target model.

Te-Yi (Dexter) Kan · Sole contributor, with research guidance from my advisor

System architecture ↓Explore preliminary results ↓Qualifying exam & slides

01 / THE PROBLEM

When should the cloud verify?

Edge-only generation limits answer quality. Sending every draft span to a larger model increases cloud usage. This project explores the accuracy–cloud usage tradeoff through selective verification.

02 / MY CONTRIBUTION

Independent design and implementation

I am the sole contributor responsible for system design, implementation, and experimental evaluation, with research guidance from my advisor. I developed a local gate, constructed semantic-divergence labels, and evaluated confidence features and additional feature variants.

03 / SYSTEM ARCHITECTURE

Draft, gate, and selectively verify

  1. Draft locally. Qwen2.5-1.5B-Instruct generates an 8-token span using greedy decoding.
  2. Estimate divergence. An XGBoost classifier uses locally available features to decide whether cloud verification is needed.
  3. Accept or verify. Accept selected spans locally, or route them to Qwen2.5-7B-Instruct for verification.

Direct acceptance of unverified spans introduces an accuracy tradeoff. These results do not establish equivalence to target-only generation.

04 / EXPERIMENTAL SETUP

GSM8K evaluation

Models
Qwen2.5-1.5B-Instruct drafter / Qwen2.5-7B-Instruct target
Decoding
Greedy; generation span K = 8; reported cloud verification context window = 8 tokens
Dataset
GSM8K: 7,473 training questions and 1,319 test questions
Gate labels
20,000 edge-generated training spans. From the same accepted context, the target independently generates a reference span. MPNet (all-mpnet-base-v2) embeddings label semantic divergence using cosine similarity.
Base features
Minimum, mean, and maximum of token maximum probability, entropy, and Top-1–Top-2 probability gap: 9 features total
Additional variants
Temperature perturbation, confidence slope, within-span variation, and their combination
Gate training
XGBoost binary classifier: 200 estimators, depth 4, learning rate 0.05, subsample 0.80, column subsample 0.80, minimum child weight 5, L2 regularization 1.0; AUCPR evaluation and 20-round early stopping
Deployment
The gate uses local features only. MPNet and cloud reference spans are used for label construction, not gate inference.
Evaluation hardware
RTX 4090 Pro (researcher-reported hardware designation)

Measured preliminary accuracy and cloud usage results supplied by the researcher. This evaluation does not include a measured network deployment or end-to-end latency.

05 / PRELIMINARY RESULTS

Accuracy versus cloud usage

At cosine threshold 0.8, the extended gate achieves 72.21% GSM8K accuracy at a 27.00% cloud call rate, a 10.95 percentage-point accuracy improvement over edge-only generation. Cloud call rate is the percentage of 8-token draft spans routed for cloud verification.

06 / CURRENT SCOPE & NEXT STEPS

What these results establish

The current experiments evaluate answer accuracy and cloud invocation frequency. Selective verification improves on edge-only accuracy while using the target less often than Always Cloud, with a remaining accuracy gap to both cloud baselines.

End-to-end latency, communication volume, network overhead, and deployment across physical edge and cloud devices remain to be evaluated. Cloud call reduction alone does not establish latency speedup or a proportional reduction in serving cost.
